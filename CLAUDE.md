# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**FUNDAL** (Fortran UNified Device Acceleration Library) is a pure Fortran library providing a unified API for GPU/accelerated device memory management using either OpenACC or OpenMP backends. Users write code against a single API; the backend is selected at compile time via C preprocessor macros.

## Build System

The primary build tool is **FoBiS** (`fobis`, 3.8+, double-dash CLI). The `makefile` is a working alternative that
mirrors the fobos compiler templates.

### FoBiS

```bash
fobis build --lmodes                       # list all modes
fobis build --mode fundal-test-oac-nvf     # NVIDIA nvfortran + OpenACC
fobis build --mode fundal-test-omp-ifx     # Intel IFX + OpenMP
fobis build --mode fundal-test-oac-gnu     # GNU gfortran + OpenACC (CI coverage mode)
fobis build --mode fundal-test-omp-amd     # AMD Flang + OpenMP
fobis build --mode fundal-test-gnu         # gfortran, compile-time CPU mode (no backend macro)
fobis clean --mode fundal-test-oac-nvf     # clean (exe/ is shared by all modes: clean before switching toolchain)
```

The modes build the library sources and the tests of `src/tests` into `exe/` (objects `exe/obj/`, modules `exe/mod/`).
The `*-mpi-*` modes also build `fundal_mpih_object` and `src/tests/mpi/`.

### make

```bash
make COMPILER=gnu|nvf|ifx|amd BACKEND=none|oac|omp [GPU=cc89|gfx90a|...] [MPI=1] [lib|tests|clean]
```

Output: `build/<COMPILER>-<BACKEND>/{libfundal.a, mod/, obj/, tests/}` (gitignored, never touches `exe/`). `MPI=1`
compiles everything with `$(MPIFC)` (default `mpif90`) and adds `fundal_mpih_object`.

### Running tests

```bash
bash scripts/run_tests.sh                  # run every program of exe/ (MPI ones, name contains "mpi", with mpirun -np 2)
fobis rule --ex run-tests                  # the same
fobis rule --ex build-run-tests-oac-nvf    # clean + build + run (also -omp-ifx, -oac-gnu, -omp-amd)
```

`scripts/run_tests.sh` judges a test by its **exit status** (0 = pass; `<name>.result`, if present, must match the
output); programs with `_xfail_` in the name must exit non-zero. It does not look for "test passed". Several older tests
`stop` (status 0) on failure.

### Documentation

```bash
bash scripts/docs_examples.sh              # build + run docs/examples/src/*.F90, regenerate snippets/ and output/
fobis rule --ex makedoc                    # API pages (formal) + VitePress build
fobis rule --ex deldoc                     # clean documentation artifacts
```

Every Fortran sample and output in `docs/` is included from `docs/examples/snippets|output`, generated by
`scripts/docs_examples.sh` (gfortran through the MPI wrapper `$MPIFC`, OpenACC backend, runs on the host with
`ACC_DEVICE_TYPE=host`, MPI examples on 2 ranks). The `docs-examples.yml` workflow fails if they are stale. Never
hand-write Fortran in the pages except reference signatures.

## Architecture

### Backend abstraction via C preprocessor

The core abstraction mechanism is in `src/lib/fundal.H`. Compile-time macros select the backend:

- `DEV_OAC` — OpenACC (`acc_malloc`, `acc_free`, ...); requires `COMPILER_NVF` (`DEVICEVAR`=`deviceptr`) or
  `COMPILER_GNU` (`DEVICEVAR`=`present`)
- `DEV_OMP` — OpenMP (`omp_target_alloc`, ...); `DEVICEPTR`=`has_device_addr`, `OMPLOOP`=`target teams distribute
  parallel do`; `DEV_HIP` adds HIP-runtime device queries (AMD)
- Neither — compile-time CPU mode (`malloc`/`free`, `DEVICEVAR`=`DEVICEPTR`=`shared`, `OMPLOOP`=`parallel do`)

Kernel pattern: `!$acc parallel loop DEVICEVAR(a)` followed by `!$omp OMPLOOP DEVICEPTR(a)`.

### Source layout

```
src/lib/          - Library modules
src/tests/        - Test programs (README.md lists them)
src/examples/     - Minimal usage example
docs/examples/src - Documentation example programs (tutorial heat_1..7, cookbook)
compilers_proofs/ - Standalone tests verifying compiler feature support
```

### Module hierarchy

`fundal.F90` is the single public-facing module. It re-exports everything from the implementation modules:

- `fundal_dev_alloc.F90` / `fundal_dev_alloc_unstructured.F90` — device memory allocation
- `fundal_dev_alloc_replace.F90` — free-safe (re)allocation
- `fundal_dev_free.F90` / `fundal_dev_free_unstructured.F90` — deallocation (registry-checked)
- `fundal_dev_memcpy.F90` / `fundal_dev_memcpy_unstructured.F90` — host↔device transfers (incl. transposed)
- `fundal_dev_assign.F90` — allocate-and-copy (always reallocates; lbounds-first variants keep bounds)
- `fundal_dev_handling.F90` — device init, host fallback, query, selection
- `fundal_registry.F90` — allocation registry (address, bytes, device, label; policy off/warn/error)
- `fundal_transpose_array.F90` — host transposition used by the transposed copies
- `fundal_utilities.F90` — `bytes_size`
- `fundal_env.F90` — global state (`mydev`, `devtype`, `devs_number`, `dev_memory_avail`, `dev_memory_total`, ...)
- `fundal_mpih_object.F90` — MPI handler class for multi-device scenarios (built only with MPI)

### Two memory models

- **Structured**: purely device-allocated memory, returned as Fortran pointers (`dev_alloc`, `dev_free`, `dev_memcpy_*`)
- **Unstructured**: host allocatable arrays mapped to device (`dev_alloc_unstr`, `dev_free_unstr`, `dev_memcpy_*_unstr`)

### Preprocessor-based generics

Type/rank combinations are generated via `.INC` include files that are `#include`-d inside module `contains` sections. This avoids repetitive boilerplate. Supported numeric kinds: `R8P`, `R4P`, `I8P`, `I4P`, `I2P`, `I1P`. Supported array ranks: 1–7. FoBiS does not track `.INC` changes: touch the including `.F90` or clean.

### fobos build modes

The `fobos` file uses template inheritance to avoid duplication. A mode like `fundal-test-oac-nvf` extends `template-oac-nvf` (compiler flags), which extends `template-base` (directory layout). When adding a new mode or compiler, follow the existing template pattern and keep the makefile templates in sync.
